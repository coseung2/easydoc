# HWPX preview blank pane and blocked visual verification

- Date/timezone: 2026-09-11, Asia/Seoul (UTC+09:00); implementation began on September 10.
- Status: resolved for the blank-pane defect (fix verified 2026-09-11, KST); Hancom's own automation leg remains blocked by the local security prompt.
- Initial symptoms: the Electron preview test found two nonzero-sized PDF canvases and passed, but the initial `e2e/artifacts/screenshots/hwpx-preview-saved.png` captured an empty gray pane. Canvas existence and dimensions did not prove visible output. The final screenshot has been replaced with verified visible output.
- Impact: a width change temporarily hid the rendered PDF. This defect is resolved and visually verified; generated HWPX editing and saving remain verified. The separate live Hancom automation limitation remains open.
- Initial evidence: engine tests 61 passed; Docs HWPX generation/save/roundtrip tests 23 passed; preview hook/pane tests 9 passed; preview service tests 27 passed. Docs and Shell builds and typechecks passed. The two Electron tests passed their original assertions, followed by failed human-visible screenshot review.
- Timeline: the parent inspected the passing E2E screenshot, identified the blank pane, and requested viewport and visible-page assertions plus a layout/render fix. The Kiro Opus worker then failed with HTTP 403 (`AccessDeniedException`, invalid bearer token). One retry through the same model failed identically. The alternate worker catalog could not be refreshed (HTTP 429); no unapproved model was substituted.
- Response: preserve the source changes and build artifacts; report the visual defect and authentication blocker rather than declaring completion. No credentials or provider settings were changed, and no commit or push was made.
- Recovery plan completed for the preview UI: run a fresh explicitly selected Kiro Opus xhigh worker after authentication recovery, reproduce the visibility failure, fix the cause, assert page visibility within the right workspace, inspect rendered paper/text, and rerun save/refresh/error-recovery E2E checks.
- Confirmed cause: `HwpxPreview`'s draw effect cleared the pages host in its cleanup (`host.replaceChildren()`) and re-appended pages only as the new render finished. The effect re-runs on the observed pane width, so every width change emptied the pane for the duration of a full pdf.js re-render. Measured in the built app: collapsing the AI dock (a 180 ms width animation) produced 56 blank animation frames out of 569, from 15 ms to 384 ms after the click, while the status bar still read `저장본 기준, 한컴 12.0.0.3146 변환`. An independent run against the pre-fix build measured 66 blank frames ending at 326 ms. A screenshot taken inside that window captures the empty gray pane originally reported.
- Restored invariant: pages already drawn stay on screen until the replacement set is complete, so a width change never empties the pane. A first paint, or a newly rendered file, still appends pages progressively because there is nothing to preserve. Bytes that no longer exist (document switched away, render failed) still clear the pane.
- Second, related accuracy fix: because a redraw now keeps the old pages, the pane tracks which PDF bytes it actually painted and reports `appHwpxPreviewRendering` until the newest bytes are drawn, so a save cannot be labelled "rendered by Hancom <version>" while the previous revision is still on screen. A width-only redraw keeps the saved-render status, and a draw failure outranks the busy state.
- Recovery verification (2026-09-11): the focused preview hook/pane suites passed 14 tests; the worker also verified `tsc --noEmit`, Prettier, ESLint and the English-comment check for the changed files. `e2e/skills-hwpx.spec.ts` passed both tests against a fresh Docs build. The Electron test now requires the first page to be at least 20% in the viewport, polls the canvas's own pixels for >500 dark glyph pixels on a >90% white sheet, samples every animation frame across an AI-dock collapse and requires zero blank frames, and settles two frames before the screenshot. `e2e/artifacts/screenshots/hwpx-preview-saved.png` was inspected and shows the white page with the fixture text.
- Independent confirmation (2026-09-11): a separate rebuild and rerun by the reviewing session reproduced the same result — 14 preview unit cases and both Electron tests passing in 16.2 s with zero blank frames across the dock collapse, against the 66 blank frames the same test measured on the pre-fix build.
- Residual limits: the pixel assertions describe the controlled fixture PDF, not Hancom's own output; the E2E still replaces the `docs:preview-hwpx` handler, so the live Hancom leg is unverified. The earlier untracked scratch diagnostic was archived as `.task/hwpx-preview-spike/legacy-e2e-diag.spec.ts` outside normal E2E discovery.
- Separate limitation: final Hancom automation remains blocked by the local per-file security prompt. The one exploratory PDF success is not proof of dependable final-helper operation; see `docs/hwpx-preview-verification.md`.
- Prevention: visible document output is an acceptance condition. Canvas count, dimensions, and successful IPC alone are insufficient — assert viewport presence and drawn pixels, and treat "never blank while re-rendering" as part of the contract for any pane that redraws on a measured size.
